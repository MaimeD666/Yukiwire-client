# Решения и сохраняемые контракты

Актуализировано: 2026-10-16. Ниже зафиксировано существующее поведение по коду и локальной истории проверок. Ниже также фиксируется текущая архитектура исправлений; статус реализации не заменяет живую приёмку. Новое решение оформлять с причиной, затронутыми сценариями, проверкой и ссылками на реализацию; заменённое явно помечать.

## D-001. Совместный TUN и системный прокси

**Состояние:** реализовано; сохранить при переработке.

`tun_system_proxy` — отдельная настройка, по умолчанию выключена и сохраняется при смене режима. В `capture='tun'` она позволяет браузерам использовать HTTP-прокси, пока остальные соединения идут через TUN. В прежней диагностике это различие путей объясняло работоспособность прокси при TLS-сбоях чистого TUN с zapret.

Прокси применяется после готовности собственного TUN и проверки основного VPN-outbound. Журнал охватывает оба изменения сети. При пересмотре постоянных портов/локальных inbound сохранить этот сценарий и передавать актуальный endpoint во все зависимые компоненты.

Источники: `routing.DEFAULTS`, `backend.Session.start`, `network.NetworkGuard`, `network._recover_journal`; проверки — `tests/test_service.py`, `tests/test_network.py`, `tests/test_routing.py`. Границы живой проверки описаны в [state.md](state.md).

## D-002. Диагностика различает пути и уровни успеха

**Состояние:** реализовано.

`health.check_sites(capture='tun')` использует прямое HTTPS-соединение без явного прокси, проходя через системный маршрут TUN. При ошибке отдельно сравнивает основной VPN-outbound через диагностический listener. Даже при включённом системном прокси эта проверка сохраняет назначение: выявить проблему именно TUN.

Проверка готовности VPN использует принудительный outbound, чтобы split routing не дал ложное подтверждение через direct. Успешный TLS с HTTP 403 подтверждает транспорт, но не доступ к странице; HTTP 200 страницы не доказывает воспроизведение видео. Смена архитектуры диагностического порта должна сохранить эти различия.

Источники: `health.diagnostic_config`, `health.check_sites`, `backend.Session.probe`, `backend.ApplicationService._probe`; `tests/test_health.py`, `tests/test_core_integration.py`.

## D-003. Восстановление по владению сетью

**Состояние:** реализовано; прежний механизм повышения прав заменён в D-007.

Перед захватом создаётся устойчивый журнал с идентификатором lease, PID и временем создания процессов; watchdog и задача следующего входа позволяют повторить очистку после аварии. Ядро привязано к Job Object. TUN получает уникальное имя/описание, очистка проверяет его идентичность.

Прокси восстанавливается только при соответствии ожидаемому собственному состоянию. Если пользователь или другой клиент сменил прокси, новое значение сохраняется, но очистка собственного TUN всё равно выполняется. Неподтверждённое завершение ядра или неполная очистка сохраняет владение/журнал и препятствует повторному захвату.

При изменении восстановления или установщика сохранять аварийные сценарии и незавершённое состояние. Прежний запуск изменяемого Python с повышенными правами исключён из production (D-007).

Источники: `yukiwire/network.py`, `yukiwire/process.py`, `yukiwire/watchdog.py`, `yukiwire/startup.py`, `scripts/recover-tun.ps1`; `tests/test_network.py`, `tests/test_service.py`, `tests/test_watchdog_integration.py`.

## D-004. Сохранённые и активные настройки разделены

**Состояние:** реализовано.

`reconnect_on_change=False` позволяет сохранить изменения без остановки активного VPN. `settings_pending` сообщает, что они ещё не применены. `auto_reconnect` управляет восстановлением после сбоя и не заменяет этот переключатель.

При автоприменении Xray проверяет кандидата до записи и отключения. После успешной очистки запускается та же выбранная конфигурация профиля с новыми настройками; допустимый сбой допускает одну попытку вернуть старые настройки сессии, сохранив новый черновик. Отмена, чужой захват или неоконченная очистка запрещают повторный запуск. События привязаны к поколению сессии.

Прежний handoff всего backend в повышенный процесс заменён D-007. Переключение в TUN остаётся переходом той же обычной Python-сессии; повышается только native helper.

Источники: `backend.ApplicationService._command`, `_apply_settings`, `_started`, `routing.connection_settings`, `native/WebShell.cs`; `tests/test_settings_apply.py`, `tests/test_service.py`.

## D-005. Маршрутизация и игровые исключения

**Состояние:** реализовано.

Явная блокировка выше игрового исключения; игры выше пользовательских VPN/direct-исключений. Выключение игрового режима сохраняет список процессов. Имена/полные пути `.exe` сопоставляются с учётом регистра; в исходном JSON эти правила не применяются.

Обычные прокси и TUN используют общую политику маршрутов. В local/system правила охватывают только пришедший в прокси трафик; захват всего TCP/UDP требует TUN. Принудительный диагностический outbound служит отдельной цели (D-002), поэтому тестировать только его недостаточно.

Источники: `routing.build_rules`, `routing.parse_game_processes`, `routing.explain`; `tests/test_routing.py`, `tests/test_game_integration.py`.

## D-006. Граница UI, конфигурация и приватные данные

**Состояние:** границы реализованы; текущие результаты production-проверок — в state.md.

UI загружается с локального origin WebView2, команды ограничены явным списком. Обычный хост запускает браузер без повышения прав, включая запросы из TUN-сервиса. Прежний помощник запускал весь Python-бэкенд; в публичной сборке этот вход удалён. Новая граница и её проверки описаны в D-007.

Импорт JSON сохраняет разрешённые секции; пользовательские inbound/API/файловые логи не исполняются напрямую. Конфигурация передаётся Xray через stdin, сохранённые профили защищены DPAPI. Упаковка использует явный список публичных файлов, а обновление/удаление оставляет приватные данные.

При новых логах, экспорте профилей, переносе установки или смягчении парсера сохранить эти границы и добавить проверку конкретного нового поведения. Не переносить секреты в документацию ради воспроизводимости.

Источники: `native/WebShell.cs`, `native/NetworkWorker.cs`, `yukiwire/config.py`, `yukiwire/storage.py`, `scripts/build_portable.py`, `scripts/build_installer.py`, `packaging/windows/Yukiwire.iss`.

## D-007. Portable UI и отдельный защищённый сетевой компонент

**Состояние:** реализовано; защищённая установка, production IPC/prepare/stop/EOF и настоящий TUN проверены на GitHub Windows VM. Интерактивное подтверждение/отмена UAC и legacy-миграция остаются отдельными сценариями.

Пользователь не выбирал устройство установки и попросил объяснить варианты. Выбран вариант, сохраняющий portable: интерфейс/профили/Python остаются в обычной папке, Xray/Wintun/минимальный native helper — в Program Files. Первый TUN устанавливает компонент через отдельный UAC, запуск helper также требует UAC один раз за время жизни backend. Отсутствие подписи принято пользователем; подпись не считается реализованной.

`build_network.py` встраивает payload в установщик; каталог версии определяется SHA256 helper. ACL допускает запись только SYSTEM/Administrators, проверяются владельцы, каждый родитель и отсутствие reparse points. Повышенный helper проверяет собственный путь и хэши payload. Не принимает Python/executable/script paths от клиента. Конфигурация идёт в памяти, перечень разрешённых полей проверяется native-кодом; маршруты/адреса/имя TUN задаются helper. Geodata копируются в защищённый snapshot с правами исходного пользователя, перед запуском ядра; наследуемая среда очищается. Неизвестные поля JSON в TUN могут быть отклонены явно, без молчаливого ослабления защиты.

Named pipe использует overlapped I/O: синхронное ожидающее чтение блокировало параллельную запись в настоящем Windows pipe. Каждая операция владеет событием и буфером до завершения отмены; close не закрывает handle под незавершённым I/O. Pipe имеет ACL пользователя/Admin/SYSTEM и запрет сети; проверяются PID/время родителя и PID helper. Helper подключается с Identification, чтобы обычный сервер не мог impersonate его административный токен. Ядро до записи обоих журналов ожидает конфигурацию на stdin, входит в Job Object; serial защищает новое ядро от позднего stop. Разрыв IPC/смерть родителя закрывают только собственное ядро; cleanup использует только созданный helper адаптер. Неоконченная очистка сохраняет журнал. Обычный Python подтверждает удаление адресов/DNS/маршрутов перед удалением своего lease и независимо восстанавливает свой proxy.

Очистка через запускаемый PowerShell заменена native IP Helper API и фиксированными командами системного netsh: в CI PowerShell не доходил до первой операции очистки. Удаляются только собственные /1-маршруты с нулевой метрикой/next hop и известные адреса на проверенном адаптере; DNS сбрасывается, адаптер отключается. Обычный процесс независимо проверяет итог. Новый helper может восстановить мёртвое ядро той же живой backend-сессии; чужой живой владелец сохраняется. Регрессии: test_broker_pipe, test_network_cleanup, verify_network_live.

Legacy-журналы не превращаются в доверенные записи helper. При неподтверждённой очистке требуется старый recovery; автоматическое удаление старых задач/активной установки пользователя не выполнялось. Требуется отдельная проверка миграции и штатное обслуживание устаревших protected components.

Источники: `native/Network*.cs`, `native/ProtectedStorage.cs`, `yukiwire/broker.py`, `yukiwire/privilege.py`, `network.tun_clean`, `scripts/build_network.py`. Проверки: `tests/test_network_policy.py`, `test_broker.py`, `test_privilege.py`; opt-in `scripts/verify_network_component.py --install` не запускает TUN, но устанавливает компонент.

## D-008. Перенос профилей и приватность

**Состояние:** реализовано; native UX экспорта/импорта требует финальной приёмки.

DPAPI остаётся форматом локального хранения. Нечитаемые файлы сохраняются и показывают понятную ошибку. Экспорт требует отдельного выбора файла и предупреждения, что резервная копия содержит ключи открытым текстом. Payload перехватывает обычный native host до WebView; он же пишет выбранный файл. Импорт проверяет все профили до одной атомарной записи, объединяет без дубликатов и сохраняет выбор. Реальные профили при разработке не экспортировались.

## D-009. DNS следует доменным маршрутам

`dns_config.py` сохраняет порядок domain-rules и разделяет direct/VPN resolver groups, ограничивая fallback (`finalQuery`, `disableFallbackIfMatch`). Physical DNS снимается до TUN, настройки позволяют заменить его IP-адресами; VPN DNS — HTTPS DoH. DNS процессов игр не атрибутируется по общему Windows resolver. Имена самого DoH/серверов используют отдельные точные bootstrap-правила, обычные запросы не получают такой fallback. Проверено настоящим Xray и локальными UDP DNS-серверами; TUN/DNS IPv6 в живой сети ещё требуется проверить.

## D-010. Постоянная опциональная блокировка при обрыве

`kill_switch=False` по умолчанию; действует в TUN/system, local сохраняет переключатель без применения. Под защитой system тоже использует только защищённый Xray. WFP-фильтры создаются транзакционно до передачи конфигурации ядру. Блокировки ALE IPv4/IPv6 connect/receive сохраняются при смерти helper и до явного release/recovery; исключения — защищённый Xray, loopback, DHCP и собственный TUN LUID. TUN permit статический, не переживает BFE/reboot; остальные фильтры постоянные. Прямые маршруты через Xray допустимы, обход ядра приложениями/LAN блокируется. Ранний boot до BFE не покрывается.

Обычный DPAPI-маркер пишется до arm, защищённый ledger — до WFP commit. Serial исключает поздние команды старой сессии. Автоперезапуск/ошибка/EOF удерживают блокировку, явное отключение/выход снимают после остановки; UI показывает «Снять блокировку» даже без ядра. Восстановление использует exact helper version из marker. Системный DNS при защите не освобождается целиком: Xray сам разрешает имена. Для WG endpoint под защитой требуется IP. На смену настройки с выключением защиты даётся явный release при применении.

Код скомпилирован, порядок journal/arm/start, авария/manual stop, ABI и принятие DNS-конфигурации ядром проверены. Настоящие WFP-фильтры проверяются на одноразовой Windows VM: system/combined, блокировка после аварии, явный release/recovery. Точные пройденные сценарии и пропуски — в state.md; BFE/reboot, полный IPv6 и старые TCP-соединения остаются отдельной матрицей. Реализация: `NetworkFilter.cs`, `NetworkKillSwitch.cs`, `killswitch.py`, `session.py`.

## D-011. Подписки, QR и диагностика остаются локальными

Подписки только HTTPS, максимум 4 МиБ/100 профилей; все записи проверяются до атомарной замены. URL хранится DPAPI и не входит в public events/экспорт профилей. Отвязка подписки сохраняет профили; активная сессия не заменяется. QR декодируется vendored jsQR локально и только открывает редактор. HTTPS-задержки проверяются отдельными local-сессиями (до 20), активное подключение влияет на измерение; под WFP-защитой сравнение отклоняется явно.

DebugTrace — выключенный по умолчанию allowlist технических полей, а не regex-маскирование произвольного stderr. Два файла по 256 КиБ, экспорт повторно фильтруется, до 1000 событий. Ошибка лога не останавливает IPC/чтение ядра. Это полезнее для переходов/категорий/таймингов, но не заменяет отдельную трассировку сетевого стека.
