## Текущая диагностика и исправление подключения

27 октября разобран отказ подключения `ConnectionResetError`. Обнаружены независимые причины: nginx на собственном VPS падал с SIGILL в libcrypto при входящем TLS, включая loopback; одновременно проверка готовности клиента зависела только от example.com, где возвращалась ошибка доверия сертификату даже через работающий сторонний клиент. Перезапуск nginx восстановил TLS; дальнейшая диагностика CPU описана ниже. Полная блокировка IP измерениями не подтверждается.

- В исходниках `health.probe_transport` проверяет до трёх HTTPS-целей через один диагностический VPN-outbound, сохраняя TLS-проверку, отмену и ошибку при отказе всех целей. `Session.start/probe` используют эту проверку; диагностика настоящего TUN не изменена. Контракт — D-002.
- На ПК оказалась более старая установленная реализация с Session в backend.py (ядро 26.9.30). В неё перенесено только это исправление, в health.py/backend.py; оригиналы лежат в `rescue-backup-20261027` рядом с установленным exe. Это локальный hotfix, не установка полного v0.5 и не новый публичный пакет. Для загрузки кода требуется полный выход из приложения через трей и повторный запуск.
- Проверены установленные функции с обоими сохранёнными профилями: HTTPS Cloudflare 200 с проверкой сертификата; через собственный XHTTP/TLS загружено 524288 байт GitHub по HTTPS 200. Собственный REALITY также дал HTTPS 200 с Firefox/Chrome. Профили/UUID/адреса не записывались в документы или фикстуры.
- Сайт на VPS снова отвечает HTTPS 401 с авторизацией; пять повторных loopback TLS-запросов прошли без новых падений nginx. Xray и сервис сайта активны. Telegram-monitor сначала остановлен, затем выведен из рабочих каталогов после отделения зависимостей сайта; подробности ниже.
- Текущее дерево: `test_health` 16, `test_service` 30, `test_settings_apply` 15, `test_network` 24 — **85 tests OK**; `test_core_integration` — **7 tests OK**, настоящее ядро и локальные фикстуры без захвата сети. Полный discover не запускался. Живой TUN/combined и игра после hotfix ещё не проверены; активный NekoBox и zapret не останавливались.

Пользователь подтвердил: после перезапуска Yukiwire всё заработало. Сохранены combined-режим и включённое direct-исключение dota2.exe. Это пользовательское подтверждение подключения, не инструментальная проверка игрового TCP/UDP или длительного видео. Дальнейшая диагностика не должна перезапускать его VPN, менять маршруты или отключать фильтры во время игры.

## Проверка VPS после восстановления, 27 октября

- Рабочая схема: TLS/IP-сертификат + HTTP/2 + XHTTP stream-one за nginx, клиентский Firefox, стандартный XMUX без mux.cool; отдельно сохранён REALITY/Vision. BBR/fq уже включены, память/диск с запасом, firewall открывает только SSH/HTTP и два используемых TLS-порта; backend сайта/XHTTP слушают loopback. Произвольное изменение fingerprint/портов/мультиплексирования не выполнялось. Свежие источники: [XHTTP/XMUX](https://github.com/XTLS/Xray-core/discussions/4113), [октябрьское обсуждение fingerprint](https://github.com/XTLS/Xray-core/issues/7131). Это не гарантия незаметности и не измерение всех операторов РФ.
- Установлена непосредственная причина SIGILL: аварийный RIP nginx в libcrypto указывает на `SHA256RNDS2` (opcode `0f38cb`). Linux сохраняет boot-флаг sha_ni, но текущий CPUID(7,0).EBX[29] равен 0; новый OpenSSL также не включает этот путь. Наблюдение согласуется со сменой возможностей виртуального CPU/миграцией VPS; действия хостера напрямую не подтверждены. Дамп читался только в памяти на сервере, приватное содержимое не экспортировалось. Старый процесс сайта также упал с SIGILL и восстановился systemd; Xray/nginx в этой проверке не перезапускались.
- Для следующих запусков nginx/yukiwire-site добавлены systemd drop-in `60-yukiwire-cpu-compat.conf` с `OPENSSL_ia32cap=:~0x20000000`: отключается только аппаратный SHA-путь. Проверены SHA256, nginx -t, systemd-analyze verify; daemon-reload не сменил PID служб. Параметр ещё не загружен текущими процессами; свежие процессы сейчас корректно определяют CPUID. Это не замена исправлению стабильности CPU у хостера.
- Сайт переключал режимы через импорт Telegram bot.py. Нужные функции отделены в `/opt/yukiwire-site/mode_control.py`, helper использует `/etc/yukiwire-mode.env` только с параметрами VPN, без TG/Gemini-секретов. Бот, прежний env и unit перемещены в root-only `/root/yukiwire-retired-20261027`; бот отсутствует как загружаемый unit. Оригинальный helper сохранён там же. Проверены оба кандидата tcp/xhttp закреплённым серверным ядром; TLS fallback и identity сохранены. Вызов helper для уже активного режима успешен до/после удаления бота, статус обновлён, активный JSON побайтно и PID xray/nginx сохранены. Настоящее переключение режима во время игры не выполнялось.
- Действующий Xray на VPS — 26.3.27. Официальный 26.10.21 подготовлен отдельно в `/root/yukiwire-maintenance/v26.10.21/xray`, архив сверён с SHA256 asset из GitHub API; все три действующие конфигурации приняты `run -test`. Активный binary/service не заменены, живой handshake новым ядром ещё не проверен. [Релиз upstream](https://github.com/XTLS/Xray-core/releases/tag/v26.10.21) рекомендует обновление; установка потребует отдельного окна с переподключением.
- IP-сертификат действует до 30 октября, shortlived/webroot и таймер Certbot настроены, deploy hook делает reload nginx. Локальный ACME webroot и `certbot renew --cert-name yukiwire-ip --dry-run --no-random-sleep-on-renew` прошли: exit 0, simulated renewals succeeded; production-сертификат и PID Xray/nginx не изменились. Такие сертификаты имеют срок 160 часов: [Let’s Encrypt](https://letsencrypt.org/2026/01/15/6day-and-ip-general-availability). Сайт на том же IP не является независимым каналом при блокировке самого IP; отдельным резервом остаётся консоль провайдера.

## Реализованный объём

- Повышенный Python исключён из production. UI/Python остаются обычными, native helper/Xray/Wintun устанавливаются отдельно в защищённый Program Files. Ограниченные IPC/policy, проверка ACL/владельца/хэшей, Job Object, защищённый журнал. Старый worker есть только в test host. Production IPC/сеть проверены в CI; подробнее D-007.
- Случайные endpoints с auth SOCKS/probe/metrics; pure TUN без обычных прокси, combined сохраняет HTTP для WinInet. Общий HTTP без auth остаётся ограничением для локальных процессов. Метрики читаются HTTP, без statsquery subprocess.
- Опциональный persistent WFP kill switch для system/TUN: journal-before-arm, удержание блокировки при аварии/reconnect, явное снятие даже без ядра. По умолчанию выключен. Реальные WFP-фильтры и аварийное восстановление проверены в CI; D-010 содержит ограничения.
- Раздельный direct/VPN DNS, HTTPS-подписки с атомарным DPAPI-хранением, локальный QR, отдельные HTTPS-замеры профилей, перенос JSON через native host, добровольный ограниченный технический журнал без raw stderr/секретов.
- Парсер понимает дополнительные метаданные/HTTPUpgrade/REALITY, Hysteria2+Salamander, базовый KCP, userspace WireGuard JSON. Удалённый ядром H2, неработающий legacy KCP seed и отключение TLS-проверки отвергаются явно.
- Сериализация переходов, поколения и независимые cancel Events; поздние события не запускают новое соединение. Session/validator вынесены в session.py, dispatcher — именованные handlers. Подписки/замеры не держат lock состояния во время сети.
- Обновление/откат правил при активной сессии, immutable CDN fallback, закреплённый bundled RU snapshot с ru-blocked. Сборка не перезаписывает source runtime/core geodata.
- Независимый SHA256 Xray, ручная проверка обновлений, единая версия, production без test hooks. Release собирает/проверяет артефакт того же запуска, проверяет точный набор/хэши; Actions закреплены SHA.
- Setup содержит полный подписанный offline WebView2 x64; .NET 4.8 требуется заранее. Отдельная тестовая регистрация/mutex установщика не затрагивает активную установку пользователя.

## Исправления, найденные при живой приёмке

- Синхронный Windows named pipe блокировал запись при ожидающем чтении. Переведён на overlapped I/O с отдельными событиями/буферами и завершением отмены до освобождения handle. Настоящий pipe проверяет duplex, 256-КиБ кадр, cancel read/connect, лимит кадра и PID.
- Запускаемый native helper PowerShell не доходил до очистки TUN в CI. Очистка заменена `NetworkCleanup.cs`: точные IP Helper rows, только собственные маршруты/адреса; системный netsh сбрасывает DNS и отключает проверенный адаптер. Python независимо подтверждает восстановление.
- `RemoteProcess.poll` проверяет PID + время создания даже при живом IPC: умершее ядро с незавершённой очисткой больше не считается работающим. Новый helper восстанавливает stale lease того же живого backend, сохраняя чужого живого владельца.

## Оставшиеся ограничения и приёмка

Не проверены интерактивное согласие/отмена UAC (на hosted VM UAC отключён), реальный IPv6 интернет, старые TCP-потоки, BFE restart/reboot, sleep/resume, перенос между Windows-аккаунтами, чистая offline-машина без WebView2 и длительное YouTube-видео с конкретным zapret. HTTP/TLS и счётчики доказывают сетевой путь, не воспроизведение видео.

Общий HTTP WinInet остаётся без auth ради совместимости Windows-прокси; SOCKS и служебные endpoints защищены. Собственные binaries не подписаны. Обновления устанавливаются вручную. Legacy TUN-журнал восстанавливается прежним клиентом; старые защищённые версии автоматически не удаляются. Не описывать эти границы как «аудит полностью закрыт».
